# Quelyra README 与中文注释改造设计

## 目标

将 Quelyra 当前的英文骨架说明改造成面向最终成品的中文工程型文档，并把代码、配置和目录占位文件中的英文用途注释统一改为清晰、自然、可维护的中文说明。

## README 定位

根 README 采用“成品宣传型”口吻，主要面向未来的面试官、开发者和项目使用者。功能描述按照项目最终形态编写，但不伪造性能数字、用户数量、线上地址、截图、测试结果或 CI 状态。

尚未具备真实内容的徽章、演示地址和产品截图使用 HTML 注释预留，不在 GitHub 渲染结果中展示。快速开始部分给出最终预期的 Docker Compose 工作流，并在后续实现过程中校准服务名、环境变量和命令。

## 根 README 信息结构

1. 项目名称、标语与一句话定位。
2. 项目解决的问题与适用场景。
3. 核心能力和差异化设计。
4. Mermaid 系统架构图。
5. 从自然语言问题到可信答案的处理流程。
6. Python、Go、Vue3 以及基础设施技术栈。
7. Monorepo 目录结构及各模块职责。
8. 快速开始、环境要求和配置方式。
9. 安全边界与查询治理能力。
10. Agent 评测指标与评测目录。
11. 开发、测试与契约管理约定。
12. 路线图、常见问题、许可证和致谢。

## 文案风格

- 中文为主，保留不可避免的技术名称，例如 LangGraph、FastAPI、Gin、Vue 3、OpenAPI。
- 先说明价值，再介绍实现；减少空泛的“大模型赋能”等宣传表达。
- 对安全、可追踪、可评测和语义层能力给出工程化解释。
- 不把 Monorepo 描述成进程耦合：明确三个应用独立构建、运行和部署。
- 不宣称尚未测量的准确率、延迟、吞吐量或成本收益。

## 子目录 README

现有 35 个 README 全部改为中文。根 README 负责产品和全局架构；服务 README 负责本服务边界；功能目录 README 只说明目录所有权和内容放置规则，避免重复大段全局介绍。

## 中文注释规范

- Python、YAML、TOML、Makefile 等使用 `# 用途：……`。
- Go、TypeScript 和 Go Module 使用 `// 用途：……`。
- Vue 与 HTML 使用 `<!-- 用途：…… -->`。
- CSS 使用 `/* 用途：…… */`。
- `.gitkeep` 使用与文件格式兼容的中文说明。
- JSON 不支持注释，`package.json` 和 `tsconfig` 继续保留合法的空对象，并由相邻 README 解释。

注释描述文件承担的职责，不描述尚不存在的实现细节，也不使用“工具类”“处理相关逻辑”等模糊措辞。

## 验收标准

- 根 README 包含完整项目结构、架构图、核心能力、技术栈和快速开始。
- 35 个 README 不再以英文标题和英文说明为主体。
- 所有原英文用途标记均替换为中文 `用途：`。
- Python、Go、TypeScript、Vue 文件仍然只有注释，不产生业务实现代码。
- 严格 JSON 文件保持合法且内容为 `{}`。
- 全仓库扫描不得残留英文用途标记，也不得意外新增可执行声明。

## 本次不包含

- 不安装依赖或生成锁文件。
- 不实现 API、Agent、SQL 网关或前端页面。
- 不制作虚假的产品截图、徽章和性能报告。
- 不初始化 Git 仓库，不创建提交或远程仓库。
